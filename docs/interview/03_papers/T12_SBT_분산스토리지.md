# T12 — 파일 분산 저장 방식을 활용한 경제적이고 효율적인 SoulBound Token 구현

> **Implementation of SoulBound Token Using Economical and Efficient Decentralized File Storage Methods**
> 정보보호학회논문지 (JKIISC), Vol. 34, No. 6, pp. 1345–1356 (2024. 12) · 공저(2/4)

## 0. 30초 요약

> **이 논문은 저희 3D 계측 연구와 직접 이어집니다.** 신체 치수를 측정하는 기술을 쓰는 스타트업은 고객의 민감한 신체 정보를 중앙 서버에 저장해야 하는데, 기술적으로도 비용적으로도 부담이 큽니다. 유출되면 치명적이고요. 그래서 저희는 **민감정보를 IPFS에 분산 저장하고, 그 파일을 가리키는 주소인 CID만 SoulBound Token에 담아 고객에게 주는** 방식을 제안했습니다. SBT는 양도가 불가능하니 남에게 탈취당하지 않고, 스타트업은 고객 이름과 컨트랙트 주소만 보관하면 됩니다. 필요할 때 CID를 받아와 확인하고 쓴 뒤 폐기하면 되니 보안 부담이 사라집니다. 열람 권한은 사전 승인된 계좌에만 주고 조회 기록이 블록체인에 남습니다. 비용 문제는 이더리움 메인넷 대신 Layer2인 Optimism을 써서 가스비를 **1/4300 수준**으로 낮췄습니다.

## 2. 왜 이 연구를 했나 — 가장 중요한 절

### 이 논문이 다른 연구와 연결되는 지점

**논문 서론에 결정적인 문장이 있다.**

> 최근 **신체 치수 측정, 얼굴 위변조 판별**과 관련된 기술들이 지속적으로 연구되지만, 개인의 민감정보인 **의류 사이즈를 측정하는 경우[13]** 와 **얼굴 변조 여부[16]** 등의 기술을 활용하는 스타트업에서는 **중앙화된 서버에 고객의 데이터를 저장하는 방식이 기술적, 비용적으로 부담이 큰 상황**이다.

**인용된 두 문헌이 무엇인지 확인하면 이 논문의 위치가 명확해진다.**

| 인용 | 문헌 |
|------|------|
| 의류 사이즈 측정 | **"Automatic size measurement of garments using vision deep learning models and point-cloud data"** → **[T04 논문](T04_의류치수_포인트클라우드.md)** |
| 얼굴 위변조 판별 | **"CloudNet: A LiDAR-based face anti-spoofing model that is robust against light variation"** → 같은 연구실의 다른 논문 |

**즉 이 블록체인 논문은 같은 연구실이 만들어 낸 계측 기술의 후속 문제를 다룬다.**

```
3D 계측 연구 (T03, T04, T05)
   → 신체 치수·의류 치수를 측정하는 기술을 만들었다
        ↓
   그 기술을 쓰는 스타트업은 고객의 민감한 신체 정보를 갖게 된다
        ↓
   그 데이터를 어디에, 어떻게 안전하게 보관할 것인가?
        ↓
T12: IPFS + SoulBound Token으로 저장 (2024.12)
        ↓
T13: 그 토큰을 잃어버리면 어떻게 복구할 것인가 (2025.04)
```

**이것이 "왜 블록체인 논문도 있느냐"는 질문에 대한 결정적인 답이다.** 도메인이 갑자기 바뀐 것이 아니라, **자기 연구가 만들어 낸 문제를 다음 단계로 이어받은 것**이다. 9절에서 이 답변 전략을 정리한다.

### 문제 상황 — 스타트업의 딜레마

| 주체 | 문제 |
|------|------|
| **스타트업** | 고객의 민감정보를 자체 데이터베이스에 저장하면 **기술적·비용적 부담**이 크고, 유출 시 책임이 크다 |
| **고객** | 자기 신체 정보가 어디에 어떻게 쓰이는지 알 수 없다 |

### 기존 SBT 연구의 한계 — 논문의 진단

> 블록체인의 탈중앙화 특성을 이용하여 **개인정보를 SBT에 저장하는 방식이 제안되고 있으나[8] 가스비 문제와 저장 용량의 제약** 등으로 실질적인 구현이 어렵다는 한계가 존재하여, **데이터 저장이 아닌 개인의 신원 및 평판 증명 등에 국한**되어 있는 상황이다. 또한 일부 SBT에 데이터를 저장하는 방식도 존재하였으나, **데이터의 용량에 따라 가스비가 증가하는 SBT의 특성**에 따라 생성비가 과도하게 올라 연구가 진행되지 않는 상황이다.

**핵심 제약**: 블록체인에 데이터를 직접 저장하면 **용량에 비례해 가스비가 폭증**한다. 그래서 SBT는 지금까지 "증명서" 용도로만 쓰였고 "저장소" 용도로는 못 쓰였다.

### 이 논문의 해법 — 두 축

**축 1: 데이터를 블록체인 밖에 둔다**

```
민감정보 → IPFS에 분산 저장 → CID 생성
                                ↓
                       CID만 SBT에 저장
```

**용량 문제가 사라진다.** SBT에는 짧은 해시 문자열 하나만 들어가기 때문이다.

**축 2: Layer2로 비용을 낮춘다**

이더리움 메인넷 대신 **Optimism**을 써서 토큰 생성 비용을 대폭 절감한다.

### 이 구조가 각 주체에게 주는 이점 (논문 서론)

**고객 입장**
- 데이터를 열람할 수 있는 **열쇠(CID)를 직접 보관**해 안심할 수 있다
- 스타트업이 데이터를 열람할 때마다 **그 기록이 블록체인에 남아**, 추후 문제가 발생해도 쉽게 대응할 수 있다

**스타트업 입장**
- 자체 데이터베이스에 고객 민감정보를 저장해 두는 위험이 사라진다
- **고객의 이름과 contract address만 보관**하면 된다
- 필요할 때마다 CID를 받아와 IPFS에서 열람하고, **사용 후에는 데이터를 폐기**하면 되므로 보안 부담이 줄어든다

**보안 측면**
- SBT는 **양도가 불가능**하므로 고객의 SBT가 타인에게 탈취당할 가능성이 없다
- 스마트 컨트랙트로 CID 열람 권한을 **스타트업의 전자지갑 주소로만 설정**해, 외부에서 contract address를 알아도 CID 열람이 불가능하다

## 3. 사전지식 (A to Z)

### 3.1 블록체인과 이더리움

블록체인은 거래 기록을 여러 노드가 나눠 갖고 검증하는 분산 장부다. 해시함수와 탈중앙 네트워크 구조로 **DDoS 공격과 단일 지점 장애를 방지**할 수 있다.

| 단계 | 기술 |
|------|------|
| 비트코인 | 단순 거래 기능 |
| **이더리움** | **스마트 컨트랙트**와 NFT 기능 추가 |

→ 상세: [06_강화학습·시계열·기타.md](../01_foundations/06_강화학습·시계열·기타.md)의 `### 블록체인 기초`

### 3.2 IPFS — 논문 2.1절

**InterPlanetary File System.** 데이터를 여러 노드에 분산 저장해 **단일 장애 지점(SPOF)** 을 제거한다.

**작동 방식 (논문 Fig. 1)**

```
1. 파일이 IPFS에 업로드되면 여러 블록으로 분할된다
2. 각 블록이 고유한 해시값을 갖는다
3. 파일 전체의 해시값(CID)이 이 블록 해시값들을 기반으로 생성된다
4. 생성된 블록들이 IPFS 네트워크의 여러 노드에 분산 저장된다
5. 사용자가 파일을 요청하면 해시값 기반으로 블록을 검색해 조합, 원본을 복원한다
```

**CID (Content Identifier)의 핵심 성질**

> CID는 **파일의 내용을 바탕으로 결정**되므로, **동일한 파일에서는 항상 동일한 CID를 생성**하며 이를 통해 파일의 무결성을 확인할 수 있다.

**위치 기반 주소와의 차이**: 전통적 URL은 "어디에 있는가"로 주소를 지정하는데, IPFS는 **"내용이 무엇인가"** 로 주소를 지정한다(content addressing).

**IPFS의 장점 네 가지 (논문이 정리)**

1. **무결성 검증**: 해시값으로 변조 여부를 확인할 수 있다. 파일이 변경되면 해시값이 달라진다
2. **높은 가용성**: 여러 노드에 분산돼 단일 노드 장애가 전체에 영향을 주지 않는다
3. **효율적 콘텐츠 배포**: P2P 네트워크로 트래픽을 분산시켜 대규모 전달이 가능하다
4. **탈중앙화**: 중앙 서버 개입 없이 데이터 공유가 자유롭다

**IPFS의 한계 — 논문이 정확히 짚는다**

> IPFS는 **데이터를 장기적으로 보존하지 않는 노드들로 구성**되어 있기 때문에, 중요한 데이터의 경우 **유실 위험이 존재**할 수 있다. 이를 보완하기 위하여 **Pinning 서비스**를 통해 특정 데이터를 지속적으로 IPFS 상에 보존할 수 있다.

**"IPFS에 올리면 영원히 남는다"는 흔한 오해를 논문이 정확히 교정하고 있다.**

### 3.3 SoulBound Token과 토큰 표준

**SBT**: 특정 지갑에 영구히 묶여 소유자가 다른 사람에게 전송할 수 없는 NFT다.

**두 표준의 조합 — 이 논문의 구현 방식**

| 표준 | 역할 |
|------|------|
| **ERC-721** | 대체 불가능 토큰(NFT)의 기본. 각 토큰이 고유하고 상호 교환될 수 없는 속성을 정의 |
| **ERC-5192** | **토큰 잠금 기능**을 정의. SBT가 특정 지갑에 영구 귀속되도록 한다 |

**논문의 서술**: "SBT는 ERC-721 표준을 기반으로 하고, 이를 구현하기 위해 **ERC-5192 표준의 토큰 잠금 기능**이 사용된다."

> ※ 이 논문은 기존 연구들과 구현 방식이 다르다. 논문 2.3절에서 지적하듯 **"대부분의 기존 연구들이 SBT를 구현할 때 NFT의 전송 기능을 제거한 형태로 구현"** 하는데, ERC-5192 표준의 잠금 기능을 쓰면 **표준을 따르므로 안정성과 사용성이 확보된다.**

→ 상세: [06_강화학습·시계열·기타.md](../01_foundations/06_강화학습·시계열·기타.md)의 `### NFT와 SoulBound Token`, `### 스마트 컨트랙트와 토큰 표준`

### 3.4 Layer2 Solution — 논문 2.2절

**목적**: 이더리움 메인넷의 **확장성 문제**를 해결한다. 메인넷의 높은 가스비와 느린 거래 처리 속도를 개선한다.

**두 가지 방식**

| 방식 | 원리 | 장점 | 단점 |
|------|------|------|------|
| **Optimism Rollup** | 메인넷 **외부에서 트랜잭션을 처리**한 뒤 **요약된 결과만 메인넷에 기록** | **메인넷의 보안성을 그대로 유지**하면서 높은 처리 속도와 낮은 가스비 | 거래 확정 전 **일정한 검증 지연 시간** 필요 |
| **사이드체인** | 메인넷과 **독립적으로 운영되는 별도의 블록체인**. 브릿지로 연결 | 높은 유연성, 낮은 가스비 | **독립된 보안 모델**이라 메인넷 수준의 보안 제공이 어렵고, 중앙화된 노드에 의존하면 취약점 발생 |

**논문의 선택**: **"보안성 및 호환성이 더 우수한 Optimism Rollup 방식이 더 적합할 것으로 판단하였다."**

### 3.5 가스비

이더리움에서 연산과 저장에 드는 수수료다. **저장이 특히 비싸다.** 이것이 SBT에 데이터를 직접 저장하지 못하는 이유이자, 이 논문이 IPFS를 쓰는 이유다.

### 4.1 저장 방식 세 가지 비교 (논문 Table 1) — 이 논문의 논지가 압축된 표

| 비교 항목 | **중앙화 저장** | **SBT에 직접 저장** | **CID를 SBT에 저장 (제안)** |

| **데이터 수정 가능성** | **O** | X | X |
| **비용** | 유지·관리 비용 | **블록체인 저장으로 높은 가스비** | **CID 저장의 낮은 가스비 + IPFS 사용료** |
| **데이터 접근성** | 관리자가 통제 | **누구나(Everyone)** | **승인된 사용자만** |
| 데이터 무결성 | 서버 장애 시 손실 가능 | 무결성 보장 | CID가 무결성 보장, IPFS가 무결성 확보 |
| **탈중앙화** | X | O | O |

**이 표에서 읽어야 할 것**

**① "SBT에 직접 저장"의 치명적 결함이 접근성이다.**

블록체인은 **공개 장부**다. SBT에 개인정보를 직접 넣으면 **누구나 읽을 수 있다(Everyone)**. 민감정보를 다루는 목적과 정면으로 충돌한다.

**② 제안 방식이 세 가지를 동시에 만족한다.**

```
낮은 비용 (CID만 저장)
+ 접근 통제 (승인된 사용자만)
+ 탈중앙화 (중앙 서버 없음)
```

**③ 데이터 수정 불가라는 성질**

세 방식 중 중앙화만 수정이 가능하다. 블록체인 기반은 불변성 때문에 수정할 수 없다. **이것이 장점이자 단점**이다. 무결성은 보장되지만 오류를 고칠 수 없다. 8절 참조.

### 4.2 SBT 생성 절차 (논문 3.1절)

```
② IPFS 방식으로 데이터 저장
```

### 4.6 스마트 컨트랙트 함수 (논문 4.2절) — 13개

**이 목록이 이 논문의 실질적 구현 내용이다.**

| # | 함수 | 역할 |
|---|------|------|
| 1 | `constructor(string name, string symbol)` | SBT 스마트 컨트랙트 생성자. 토큰의 이름과 기호 설정 |
| 2 | **`mint(address to, uint256 tokenId, string cid)`** | **SBT를 발행한다. 소유자만 호출 가능.** 주어진 주소에 토큰이 생성되고 **IPFS의 CID를 기반으로 토큰 URI가 설정**된다 |
| 3 | `_setTokenURI(uint256 tokenId, string _tokenURI)` | 주어진 CID를 기반으로 토큰 URI 설정 (내부 함수) |
| 4 | **`_transfer(...)` override** | **토큰 전송 방지.** 항상 전송 불가능하도록 재정의 |
| 5 | **`safeTransferFrom(address, address, uint256)` override** | 안전한 전송 방지 |
| 6 | **`safeTransferFrom(address, address, uint256, bytes)` override** | 안전한 전송 방지 (오버로드) |
| 7 | **`transferFrom(...)` override** | 전송 방지 |
| 8 | `requestViewCID()` | 사용자가 CID 조회 **권한을 요청**. 권한 없는 사용자가 호출하면 **요청이 기록**된다 |
| 9 | **`approveViewer(address viewer)`** | **소유자가 특정 사용자에게 CID 조회 권한을 부여.** 요청이 존재할 때만 부여 가능 |
| 10 | **`revokeViewer(address viewer)`** | **소유자가 권한을 취소.** 취소되면 더 이상 CID에 접근 불가 |
| 11 | **`EmitCID()`** | **CID를 반환하고 조회 이벤트를 기록.** 권한이 있는 사용자만 호출 가능하며 **누가 언제 조회했는지 로그에 기록**된다 |
| 12 | **`getViewLogs()`** | **소유자가 CID 조회 기록을 확인.** 배열 형태로 반환 |
| 13 | `tokenURI(uint256 tokenId)` | 주어진 CID에 해당하는 토큰 URI 반환. 토큰이 없으면 에러 |

**핵심 설계 세 가지**

**① 전송 방지를 4개 함수에서 중복 차단한다 (4~7번)**

ERC-721의 전송 경로를 모두 막았다. `_transfer`, `safeTransferFrom` 두 오버로드, `transferFrom`이다. **하나라도 빠뜨리면 SBT가 아니게 되므로** 철저한 처리다.

**② 권한 부여·취소를 소유자(고객)가 통제한다 (9, 10번)**

논문의 설명:

> 스타트업에서 SBT를 생성할 때 **관리자의 계정에 조회 권한을 부여한 후 고객에게 SBT를 제공**하고, 추후 추가로 권한을 요청할 경우 사용한다. (approveViewer)
>
> 스타트업에서 **관리자의 계정을 변경해야 할 경우 고객이 관리자의 권한을 회수**하기 위하여 사용한다. **SBT 소유자가 직접 접근 권한을 관리하여 개인정보 유출을 방지**할 수 있다. (revokeViewer)

**데이터 주권이 고객에게 있다는 것이 이 설계의 핵심이다.**

**③ 모든 조회가 로그로 남는다 (11, 12번)**

`EmitCID`가 호출될 때마다 조회 이벤트가 기록되고, 고객은 `getViewLogs`로 **누가 언제 조회했는지** 확인할 수 있다. **감사 추적(audit trail)** 이 자동으로 만들어진다.

### 4.7 전체 운영 흐름 (논문 4.3절, Fig. 2) — 7단계

```
1) 스타트업이 메모장 파일을 업로드한다
2) IPFS 방식으로 파일을 블록 단위로 분할해 저장하고 CID를 생성한다
3) 스타트업이 CID를 바탕으로 SBT 계약을 배포한다
   ★ 이때 SBT 열람 권한을 스타트업의 계좌에만 미리 부여한다
4) 고객이 생성된 SBT를 자신의 디지털 지갑에 보관한다
5) 스타트업이 Contract Address를 바탕으로 CID를 확인한다
   ★ 이 과정이 블록에 기록된다
6) 스타트업은 CID로 정보를 확인한 후 데이터를 폐기한다
   ★ 중앙서버에 따로 저장할 필요가 없다
7) 고객은 모든 열람 기록을 언제든 확인할 수 있다
```

**6번이 이 설계의 핵심 가치다.** 스타트업이 데이터를 **보유하지 않는다.** 필요할 때 가져와 쓰고 버린다. 유출될 데이터 자체가 존재하지 않는다.

**단계별 구현 절차가 상세히 기술돼 있다** — 재현 가능성 측면에서 좋은 서술이다.

```
      DEPLOY에서 NAME(토큰 이름), SYMBOL(약어, 예: SBT) 입력 → transact
      → MetaMask 컨펌 → mint 함수에 to(주소), tokenId(숫자), CID 입력

4.4.4 생성 확인
      name, owner로 설정값 확인
      ★ 블록체인 특성상 잘못된 지갑 주소를 입력하면 되찾는 것이 불가능하므로 매우 중요한 단계

4.4.5 고객 지갑으로 가져오기
      MetaMask NFT 칸에서 'NFT 가져오기' → contract address와 토큰 ID 입력

4.4.6 스타트업에서 데이터 확인
      EmitCID 함수로 CID 확인 → 고객은 getViewLogs로 조회 기록 확인
      ★ 데이터 침해 의심 상황 발생 시 48시간 내로 감독 기관 및 데이터 주체에게 보고
```

**4.4.4의 경고가 블록체인의 근본 성질을 보여 준다.** 잘못 보내면 되찾을 수 없다. **이 문제가 정확히 T13(복구 메커니즘) 논문의 출발점이 된다.**

### 7.1 보안 요구사항 검증 (논문 Table 5)

**논문 4.6.1절의 종합**

> Pinata를 사용하여 데이터를 IPFS에 저장하고 CID를 SBT에 연동하는 방식은 중앙화된 데이터베이스보다 보안성이 뛰어나다. **CID는 파일 내용 기반의 해시값으로 생성되기 때문에 데이터 변조가 불가능**하며, 이를 통해 데이터의 무결성이 보장된다.

**운영 흐름의 요지**

> 스타트업은 데이터를 조회하여 활용하고 **CID를 포함한 모든 개인정보를 폐기**한다. 추후 데이터가 필요한 경우 **반복적으로 CID를 요청**한다. CID 요청 기록은 getViewLogs 함수를 통해 확인이 가능하다.

| Integrity and Confidentiality (무결성·기밀성) | **Compliant** |
| Accountability (책임성) | **Compliant** |
| **Data Subject Rights (정보주체 권리: 접근·정정·삭제)** | **Partially Compliant** ⚠ |
| Data Breach Notification (유출 통지) | **Compliant** |
| Security Reinforcement (보안 강화) | **Compliant** |

**논문의 설명**

> 본 시스템은 사용자의 **명확한 동의**를 바탕으로 실행하며 목적에 맞게 **최소한의 데이터만 수집**하고 목적 외 사용을 방지한다. SBT에 데이터를 직접 저장하는 것이 아닌 **CID를 저장하여 데이터를 최소한으로 저장하는 최소화 원칙**을 충족하며, IPFS 상의 데이터에 대한 **수정 권한을 제공**하여 데이터의 정확성을 유지한다. CID를 통해 **개인정보가 블록체인에 영구적으로 저장되지 않도록 제한**하며 무결성과 기밀성이 유지된다. 모든 데이터 접근과 수정은 **로그로 기록**되며 IPFS를 통해 **데이터 수정 및 삭제 권한도 부여**한다. **데이터 유출 시 48시간 이내로 고객에게 알리며** 접근 제어를 통해 보안을 강화한다.

**세 항목이 부분 준수에 그친 이유를 생각해 보면 블록체인의 근본 성질과 만난다.**

| 항목 | 왜 완전 준수가 어려운가 |
|------|------------------------|
| **Accuracy (정확성)** | 블록체인에 기록된 것은 **수정할 수 없다.** IPFS 데이터를 새로 올리면 CID가 바뀌는데, SBT에 박힌 CID는 못 바꾼다 |
| **Storage Limitation (보관 제한)** | IPFS에 올린 데이터는 **핀이 유지되는 한 남는다.** "필요 기간만 보관"이 원칙인데 통제가 어렵다 |
| **Data Subject Rights — 삭제권** | **잊힐 권리(right to be forgotten)** 와 블록체인의 불변성이 정면 충돌한다. SBT 자체를 지울 수 없다 |

**이 부분을 스스로 설명할 수 있으면 이 논문을 깊이 이해했다는 신호다.** 8.3절 참조.

### 7.4 결론과 한계 (논문 5장) — 자기 한계를 명시했다

**성과**

> 이를 통해 **신체 치수 측정 등의 기술을 활용하는 스타트업**에서 고객의 민감한 개인정보를 자체 데이터베이스에 저장할 필요가 없고, 고객에게 SBT를 부여함으로써 **고객이 열쇠를 직접 보관하며 개인정보의 사용 기록을 확인할 수 있는 투명성**도 보장된다. 또한 만약 **Contract Address가 해킹되더라도 권한이 없는 계좌는 CID에 접근할 수 없기 때문에** 해킹으로부터 안전하다.

**한계 — 매우 중요하다**

> 그러나 본 연구는 **IPFS에 저장된 데이터의 기밀성을 강화하기 위한 보안 조치가 부족**하다는 한계가 존재한다. **추가적인 암호화 기술을 적용한 방법에 대한 연구를 필요로 하며**, IPFS에 저장된 데이터의 기밀성을 보장하기 위한 **암호화 알고리즘 관련 보안 조치 연구를 제안한다.**

**향후 과제**

> 예를 들어 **의료 분야에서 환자 기록을 SBT와 IPFS에 저장하는 경우, 저장 전 데이터를 암호화하고 암호화 키를 고객의 SBT에 연동**하는 방식으로 보안성을 높일 수 있다. 또한 본 시스템을 **다양한 데이터 크기별로 비교**하거나 **실제 산업과 스타트업에 적용할 때의 실증 연구**를 제안한다.

## 8. 한계와 반박 대응

### 8.1 IPFS 데이터가 암호화되지 않았다 — 가장 치명적인 결함

**논문이 스스로 한계로 명시했지만, 그 심각성이 충분히 드러나지 않았다.**

**문제의 구조**

```
IPFS는 공개 저장소다.
CID를 아는 사람은 누구나 파일을 읽을 수 있다.
        ↓
이 시스템의 접근 통제는 "CID를 알아내는 것"만 막는다.
        ↓
CID가 한 번이라도 유출되면 데이터는 그대로 노출된다.
```

**구체적인 유출 경로**

1. 승인된 스타트업 직원이 CID를 외부에 유출
2. `EmitCID` 호출 시 CID가 트랜잭션에 노출될 가능성
3. 스타트업의 지갑 개인키 탈취
4. 논문 자체가 밝힌 대로 Pinata 같은 핀 서비스 계정 침해

**한 번 유출되면 되돌릴 수 없다.** `revokeViewer`로 권한을 취소해도 **이미 알아낸 CID는 계속 유효하다.** IPFS는 콘텐츠 주소 지정이라 CID가 곧 파일이다.

**답변 전략**: 논문이 인정한 한계이므로 그대로 짚고, 해결책을 구체적으로 말한다.

> "이것이 이 논문의 가장 큰 결함이고 논문에서도 한계로 명시했습니다. IPFS는 공개 저장소라 CID를 아는 사람은 누구나 읽을 수 있는데, 저희 접근 통제는 CID를 알아내는 것만 막습니다. CID가 한 번이라도 유출되면 권한을 취소해도 소용이 없습니다. 해결하려면 IPFS에 올리기 전에 데이터를 암호화하고, 그 복호화 키를 SBT로 관리하는 구조여야 합니다. 논문 향후 과제에서도 의료 기록을 예로 들어 이 방향을 제시했습니다."

### 8.2 잊힐 권리와 블록체인 불변성의 충돌

**GDPR은 정보주체의 삭제권(right to erasure)을 보장한다.** 그런데:

- **SBT는 지울 수 없다.** ERC-5192로 잠겨 있고 블록체인에 영구 기록된다
- CID도 블록체인에 남는다
- IPFS 데이터는 핀을 해제하면 사라질 수 있지만, **다른 노드가 캐시했다면 남는다**

논문이 Data Subject Rights를 **Partially Compliant**로 평가한 것이 이 문제다.

**대응 논리**: 논문의 설계는 **"블록체인에는 CID만, 실제 데이터는 IPFS에"** 두어 이 충돌을 완화하려 한다. 데이터를 지우면 CID는 남아도 가리키는 것이 없어진다. 다만 완전한 삭제 보장은 아니다.

### 8.3 IPFS의 영속성이 보장되지 않는다

논문 스스로 2.1절에서 지적했다. IPFS는 데이터를 장기 보존하지 않는 노드들로 구성돼 **유실 위험이 있고**, Pinning 서비스로 보완해야 한다.

**그런데 Pinning은 중앙화된 유료 서비스다.**

```
탈중앙화를 위해 IPFS를 썼는데
→ 영속성을 위해 Pinata(중앙화된 서비스)에 의존한다
→ Pinata가 서비스를 중단하면 데이터가 사라진다
```

**논문이 이 역설을 다루지 않았다.**

**답변 전략**: "IPFS를 쓴 이유가 탈중앙화인데, 데이터 영속성을 위해 Pinata 같은 중앙화된 핀 서비스에 의존하게 됩니다. 그 서비스가 중단되면 데이터가 사라질 수 있습니다. 이 역설을 논문에서 다루지 못했고, 아르위브처럼 영속성을 구조적으로 보장하는 대안이나 다중 핀 서비스 사용을 검토했어야 한다고 봅니다."

### 8.4 실증 연구가 없다

**실제 스타트업에 적용한 사례가 없다.** Remix IDE의 시뮬레이션 환경에서 기능 동작만 확인했다.

확인되지 않은 것들:

- 실제 사용자가 MetaMask를 설치하고 SBT를 관리할 수 있는가 (**사용성**)
- 고객 수가 늘어날 때의 비용과 성능 (**확장성**)
- 지갑을 분실한 고객이 얼마나 발생하는가
- 스타트업 직원의 실수로 인한 사고

논문도 향후 과제로 "실제 산업과 스타트업에 적용할 때의 실증 연구"를 제시했다.

**사용성 문제가 특히 중요하다.** 일반 소비자가 옷 치수를 재려고 MetaMask 지갑을 만들고 개인키를 관리해야 한다면, 그 자체가 도입 장벽이다.

### 8.5 데이터 크기별 비교가 없다

논문이 향후 과제로 인정했다. 실험은 **"김재현 185 75 265"** 라는 짧은 텍스트 하나로 했다.

- 데이터가 커지면 IPFS 저장·조회 성능이 어떻게 변하는가
- 3D 포인트 클라우드처럼 큰 데이터도 감당 가능한가
- Pinning 비용이 얼마나 증가하는가

**이것이 3D 계측 연구와의 연결에서 실제로 중요한 질문이다.** 신체 치수 몇 개는 텍스트지만, 3D 스캔 데이터는 수십 MB다.

### 8.6 논문 내 수치가 어긋난다

5절에서 정리한 대로 가스비 절감률이 초록(1/4300), 서론(1/4000), Table 2 계산값에서 각각 다르다.

**답변 전략**: 알고 있다는 것을 보인다. "초록과 결과에서는 1/4300, 서론에서는 1/4000으로 적혀 있고, Table 2의 절대 금액으로 다시 계산하면 또 다른 값이 나옵니다. 교정 과정에서 통일했어야 하는 부분입니다. 정확한 값은 결과 절 기준으로 메인넷 14.16달러 대비 Optimism 0.003달러입니다."

### 8.7 스마트 컨트랙트 감사를 받지 않았다

**보안 논문인데 스마트 컨트랙트 보안 감사(audit)가 없다.**

스마트 컨트랙트는 배포 후 수정이 불가능하므로 **버그가 곧 영구적 취약점**이다. 재진입 공격, 정수 오버플로, 접근 제어 미비 같은 알려진 취약점 유형에 대한 검증이 논문에 없다.

논문 4.5절에서 스마트 컨트랙트 보안 강화를 다루지만, **개인키 탈취 대응(2단계 인증 권장)** 수준이고 컨트랙트 코드 자체의 취약점 분석은 없다.

**답변 전략**: "스마트 컨트랙트는 배포 후 수정이 불가능해서 코드 취약점이 영구적 위험이 됩니다. 재진입이나 접근 제어 같은 알려진 취약점 유형에 대한 정적 분석이나 감사를 거쳤어야 하는데 논문에 그 내용이 없습니다. 보안 학회지 논문이라 이 부분이 더 아쉽습니다."

### 8.8 Layer2의 보안 트레이드오프를 충분히 다루지 않았다

논문이 Optimism Rollup의 단점으로 **"거래 확정 전 일정한 검증 지연 시간"** 을 언급했지만, 그 지연이 실제로 얼마인지(Optimistic Rollup의 챌린지 기간은 통상 7일) 그리고 그것이 이 시스템에서 어떤 의미인지는 다루지 않았다.

민감정보 조회에 7일 지연이 있다면 실용성에 영향을 준다.

## 10. 예상 질문

#### Q001. 왜 블록체인 논문도 쓰셨습니까? 다른 연구와 도메인이 완전히 다른데요. 🔴

**의도:** 연구 이력의 일관성을 묻는다. **이 논문에서 가장 중요한 질문이다.**

**답변:** 블록체인 자체가 목적이 아니었습니다. 저희 연구실에서 모바일 LiDAR로 신체 치수와 의류 치수를 재는 기술을 만들었는데, 그 기술을 쓰는 스타트업은 고객의 민감한 신체 정보를 갖게 됩니다. 키, 몸무게, 체형 같은 데이터인데 중앙 서버에 저장하면 유출 위험이 크고 관리 비용도 부담입니다. 이 논문은 그 문제를 다뤘습니다. 논문 서론에서도 저희 의류 치수 측정 논문과 얼굴 위변조 판별 논문을 인용하면서, 이런 기술을 활용하는 스타트업이 데이터 저장에 기술적, 비용적 부담을 겪는다고 문제를 설정합니다. 실제로 저장 실험에 쓴 데이터도 키 185, 몸무게 75, 신발 사이즈 265처럼 계측값입니다. 측정 기술을 만들었으니 그 결과물을 어떻게 안전하게 다룰 것인가가 다음 질문이었습니다.

**꼬리질문:** 그럼 왜 하필 블록체인이었습니까? 그냥 암호화된 데이터베이스를 쓰면 안 됩니까?

#### Q002. 왜 데이터를 SBT에 직접 저장하지 않고 IPFS를 거칩니까? 🟢

**의도:** 설계의 핵심 판단을 이해하는지 본다.

**답변:** 두 가지 이유입니다. 첫째는 비용입니다. 이더리움은 저장 용량에 비례해 가스비가 올라가는데, 개인정보를 통째로 넣으면 생성 비용이 감당이 안 됩니다. 그래서 기존 연구들도 SBT를 데이터 저장이 아니라 신원이나 평판 증명 용도로만 써 왔습니다. 둘째가 더 중요한데, 블록체인은 공개 장부입니다. SBT에 개인정보를 직접 넣으면 누구나 읽을 수 있습니다. 민감정보를 보호하려는 목적과 정면으로 충돌합니다. 저희는 데이터를 IPFS에 두고 그 파일을 가리키는 주소인 CID만 SBT에 담았습니다. SBT에는 짧은 해시 문자열 하나만 들어가니 비용 문제가 사라지고, 접근은 스마트 컨트랙트로 통제할 수 있습니다.

**꼬리질문:** 그럼 IPFS에 있는 데이터는 아무나 볼 수 있는 것 아닙니까?

#### Q003. IPFS에 저장한 데이터는 암호화하셨습니까? 🔴

**의도:** 이 논문의 가장 치명적인 결함을 짚는다. **반드시 대비해야 한다.**

**답변:** 하지 않았습니다. 논문에서도 이 부분을 한계로 명시했습니다. IPFS는 공개 저장소라 CID를 아는 사람은 누구나 파일을 읽을 수 있습니다. 저희 시스템의 접근 통제는 CID를 알아내는 것만 막는 구조입니다. 그래서 CID가 한 번이라도 유출되면 데이터가 그대로 노출되고, revokeViewer로 권한을 취소해도 소용이 없습니다. IPFS는 콘텐츠 주소 지정 방식이라 CID가 곧 파일이기 때문입니다. 제대로 하려면 IPFS에 올리기 전에 데이터를 암호화하고 복호화 키를 SBT로 관리하는 구조여야 합니다. 논문 향후 과제에서도 의료 기록을 예로 들어 저장 전 암호화하고 암호화 키를 고객의 SBT에 연동하는 방식을 제시했는데, 이 논문에서 구현했어야 할 부분이라고 봅니다.

**꼬리질문:** 그럼 이 시스템을 실제로 쓰면 위험하다는 뜻입니까?

#### Q004. SBT를 쓰는 이유가 무엇입니까? 일반 NFT면 안 됩니까? 🟢

**의도:** 기본 개념을 확인한다.

**답변:** 양도가 불가능하다는 점 때문입니다. 일반 NFT는 사고팔 수 있어서 탈취당할 수 있는데, SBT는 특정 지갑에 영구히 묶여 전송이 안 됩니다. 고객의 신체 정보에 접근하는 열쇠가 다른 사람 손에 넘어가면 안 되니 이 성질이 필수입니다. 구현은 ERC-721 표준으로 대체 불가능 토큰을 발행하고, ERC-5192 표준의 토큰 잠금 기능을 추가하는 방식입니다. 기존 연구들은 대부분 NFT의 전송 함수를 제거하는 식으로 구현했는데, 저희는 ERC-5192라는 표준을 따랐습니다. 표준을 쓰면 지갑이나 마켓플레이스 같은 외부 도구와의 호환성이 확보되고 안정성도 높아집니다.

**꼬리질문:** 전송 함수를 어떻게 막으셨습니까?

#### Q005. 전송을 막는 것을 구체적으로 어떻게 구현하셨습니까? 🟡

**의도:** 구현 세부를 아는지 본다.

**답변:** ERC-721의 전송 경로를 네 군데에서 모두 막았습니다. 내부 함수인 _transfer, safeTransferFrom의 두 가지 오버로드, 그리고 transferFrom을 각각 오버라이드해서 항상 전송이 불가능하도록 재정의했습니다. 하나라도 빠뜨리면 그 경로로 전송이 가능해져서 SBT가 아니게 되기 때문에 전부 막아야 합니다. ERC-721은 인자가 다른 safeTransferFrom이 두 개 있어서 특히 놓치기 쉬운 부분입니다.

**꼬리질문:** 그럼 잘못 발행한 토큰은 회수할 수 없다는 뜻이군요?

#### Q006. 접근 권한은 어떻게 통제합니까? 🟡

**의도:** 시스템의 핵심 기능을 설명하는지 본다.

**답변:** 스마트 컨트랙트 함수 네 개로 관리합니다. 사용자가 CID 조회 권한을 요청하는 requestViewCID, 소유자가 권한을 부여하는 approveViewer, 취소하는 revokeViewer, 그리고 실제로 CID를 반환하는 EmitCID입니다. 핵심은 권한 부여와 취소를 SBT 소유자인 고객이 직접 한다는 것입니다. 스타트업이 SBT를 만들 때 관리자 계정에 조회 권한을 부여한 뒤 고객에게 넘기고, 이후 관리자 계정을 바꿔야 하면 고객이 기존 권한을 회수합니다. 데이터 주권이 고객에게 있는 구조입니다. 그리고 EmitCID가 호출될 때마다 조회 이벤트가 기록되어서, 고객이 getViewLogs 함수로 누가 언제 조회했는지 확인할 수 있습니다. 감사 추적이 자동으로 만들어집니다.

**꼬리질문:** 조회 기록이 남는 게 왜 중요합니까?

#### Q007. 가스비를 얼마나 줄이셨습니까? 🟡

**의도:** 핵심 수치를 정확히 아는지 본다.

**답변:** 이더리움 메인넷에서 SBT 발행에 평균 14.16달러가 들었는데, Arbitrum에서는 0.07달러로 약 202분의 1, Optimism에서는 0.003달러로 약 4300분의 1까지 낮췄습니다. 거래 처리 속도도 메인넷이 10 TPS인 데 비해 Layer2는 100에서 300 TPS로 10배 이상 향상됐습니다. Optimism을 고른 이유는 Rollup 방식이 메인넷 외부에서 트랜잭션을 처리한 뒤 요약된 결과만 메인넷에 기록해서, 메인넷의 보안성을 그대로 유지하면서 비용과 속도를 개선하기 때문입니다. 사이드체인은 독립된 보안 모델이라 메인넷 수준의 보안을 제공하기 어렵습니다. 다만 논문 안에서 절감률 수치가 초록과 서론에서 각각 4300분의 1과 4000분의 1로 다르게 적힌 부분이 있어서, 교정에서 통일했어야 했습니다.

**꼬리질문:** Optimism의 단점은 없습니까?

#### Q008. GDPR의 잊힐 권리와 블록체인의 불변성이 충돌하지 않습니까? 🔴

**의도:** 법규와 기술의 근본 충돌을 이해하는지 본다. 보안 분야 면접이라면 반드시 나온다.

**답변:** 충돌합니다. 논문에서 GDPR 항목별로 자체 평가했는데, 정확성과 보관 제한, 정보주체 권리 세 가지를 부분 준수로 표시했습니다. 이유가 정확히 그 충돌입니다. SBT는 한번 발행하면 지울 수 없고 블록체인에 영구 기록됩니다. 삭제권을 완전히 보장할 수가 없습니다. 정확성도 마찬가지인데, IPFS 데이터를 수정하면 CID가 바뀌는데 SBT에 박힌 CID는 못 바꿉니다. 저희 설계가 이 충돌을 완화하는 방식은 블록체인에 CID만 두고 실제 데이터는 IPFS에 둔 것입니다. 데이터를 지우면 CID는 남아도 가리키는 것이 없어집니다. 다만 다른 노드가 캐시했다면 남을 수 있어서 완전한 삭제 보장은 아닙니다. 이건 블록체인 기반 개인정보 시스템의 구조적 한계라고 봅니다.

**꼬리질문:** 그럼 이 시스템이 GDPR을 준수한다고 말할 수 있습니까?

#### Q009. IPFS를 쓰면 탈중앙화인데, 핀 서비스는 중앙화된 것 아닙니까? 🔴

**의도:** 논문이 다루지 못한 역설을 짚는다.

**답변:** 지적하신 대로 역설이 있습니다. IPFS는 데이터를 장기 보존하지 않는 노드들로 구성돼서 유실 위험이 있고, 그래서 특정 데이터를 계속 보관하도록 고정하는 Pinning이 필요합니다. 저희는 Pinata를 썼는데 이건 중앙화된 서비스입니다. 탈중앙화를 위해 IPFS를 골랐는데 영속성을 위해 중앙화된 서비스에 의존하게 되는 구조입니다. Pinata가 서비스를 중단하면 데이터가 사라질 수 있습니다. 논문에서 IPFS의 영속성 문제 자체는 짚었지만 이 역설까지는 다루지 못했습니다. 대안으로는 한 번 지불하면 장기 보관되는 아르위브 같은 구조를 쓰거나, 여러 핀 서비스에 중복 저장하거나, 고객 본인이 자기 데이터를 핀할 수 있게 하는 방법을 생각할 수 있습니다.

**꼬리질문:** 그럼 처음부터 아르위브를 쓰는 게 낫지 않습니까?

#### Q010. 스마트 컨트랙트 보안 감사는 받으셨습니까? 🔴

**의도:** 보안 논문의 필수 요건을 짚는다.

**답변:** 받지 않았습니다. 논문 4.5절에서 스마트 컨트랙트 보안 강화를 다루기는 하는데, 접근 권한 관리와 개인키 탈취에 대한 2단계 인증 권장 수준이고 컨트랙트 코드 자체의 취약점 분석은 없습니다. 스마트 컨트랙트는 배포하면 수정이 불가능해서 코드 버그가 곧 영구적인 취약점이 됩니다. 재진입 공격이나 정수 오버플로, 접근 제어 미비 같은 알려진 취약점 유형에 대해 정적 분석 도구를 돌리거나 감사를 거쳤어야 합니다. 보안 학회지에 실린 논문이라 이 부분이 더 아쉽습니다. 다만 코드를 깃허브에 공개해서 제3자가 검증할 수 있게 한 것은 긍정적인 부분이라고 봅니다.

**꼬리질문:** 코드를 공개하면 오히려 공격자에게 유리하지 않습니까?

#### Q011. 실제 스타트업에 적용해 보셨습니까? 🔴

**의도:** 실증 연구 부재를 짚는다.

**답변:** 하지 않았습니다. Remix IDE 환경에서 기능 동작을 확인한 수준이고, 논문도 향후 과제로 실제 산업과 스타트업에 적용할 때의 실증 연구를 제시했습니다. 확인되지 않은 것들이 있는데, 가장 걱정되는 것은 사용성입니다. 일반 소비자가 옷 치수를 재려고 MetaMask 지갑을 만들고 개인키를 관리해야 한다면 그 자체가 도입 장벽입니다. 지갑을 잃어버리는 고객이 얼마나 발생할지도 모릅니다. 실제로 이 문제가 후속 논문의 출발점이 됐습니다. SBT를 분실하면 어떻게 복구할 것인가를 다룬 연구입니다. 그 외에 고객 수가 늘어날 때의 비용과 성능, 데이터 크기별 성능도 확인이 필요합니다.

**꼬리질문:** 데이터 크기가 커지면 어떻게 됩니까?

#### Q012. 3D 스캔 데이터처럼 큰 데이터도 이 방식으로 다룰 수 있습니까? 🔴

**의도:** 3D 계측 연구와의 연결에서 실제로 중요한 질문이다.

**답변:** 검증하지 못했습니다. 논문도 다양한 데이터 크기별 비교를 향후 과제로 남겼습니다. 실험에 쓴 데이터는 키, 몸무게, 신발 사이즈를 담은 짧은 텍스트 한 줄이었습니다. 3D 포인트 클라우드는 수십 메가바이트가 될 수 있어서 상황이 달라집니다. 블록체인 쪽은 문제가 없습니다. CID는 데이터 크기와 무관하게 짧은 해시 문자열이라 가스비가 그대로입니다. 문제는 IPFS 쪽인데, 저장과 조회 시간이 늘고 핀 비용이 데이터 크기에 비례해 올라갑니다. 그리고 앞서 말씀드린 암호화 문제가 큰 데이터에서 더 심각해지는데, 대용량 데이터를 암호화하고 복호화하는 비용도 고려해야 합니다. 실무적으로는 원본 스캔 데이터가 아니라 거기서 뽑은 치수 값만 저장하는 것이 현실적이라고 봅니다.

**꼬리질문:** 그럼 원본 데이터는 어떻게 관리해야 합니까?

#### Q013. 블록체인 대신 그냥 암호화된 데이터베이스를 쓰면 안 됩니까? 🔴

**의도:** 기술 선택의 정당성을 근본에서 묻는다.

**답변:** 타당한 질문이고, 사실 대부분의 경우 그쪽이 더 실용적일 수 있습니다. 블록체인을 쓸 때 얻는 것을 정리해 보면 세 가지입니다. 첫째, 조회 기록을 위변조 불가능한 형태로 남길 수 있습니다. 스타트업이 언제 데이터를 봤는지 부인할 수 없습니다. 둘째, 접근 권한을 고객이 직접 통제합니다. 중앙 데이터베이스라면 결국 운영자가 마음대로 볼 수 있는데, 이 구조에서는 고객이 권한을 회수할 수 있습니다. 셋째, 단일 장애 지점이 없습니다. 그런데 이 셋 다 대안이 있습니다. 감사 로그는 별도 시스템으로, 접근 통제는 키 관리 체계로 만들 수 있습니다. 결국 신뢰의 문제인데, 운영자를 신뢰할 수 없는 상황이나 규제상 제3자 검증이 필요한 경우에 블록체인의 가치가 생긴다고 봅니다. 이 논문은 그 전제를 충분히 논증하지는 못했습니다.

**꼬리질문:** 그럼 이 연구가 실용적이지 않다는 뜻입니까?

#### Q014. CID가 유출되면 권한을 취소해도 소용없는데, 어떻게 대응해야 합니까? 🔴

**의도:** 8.1절의 결함에 대한 해결책을 낼 수 있는지 본다.

**답변:** 근본 해결책은 암호화입니다. IPFS에 올리기 전에 데이터를 암호화하면 CID가 유출돼도 암호문만 노출됩니다. 복호화 키를 SBT로 관리하면 권한 취소가 실질적인 의미를 갖습니다. 논문 향후 과제에서도 이 방향을 제시했습니다. 여기서 설계 판단이 하나 필요한데, 키를 어떻게 관리할지입니다. 승인된 사용자마다 다른 키로 재암호화하는 프록시 재암호화 방식을 쓰면 개별 취소가 가능해집니다. 보조적으로는 조회할 때마다 데이터를 새 키로 재암호화해 새 CID를 만들고 이전 것은 핀을 해제하는 방식도 있습니다. 그러면 유출된 CID가 시간이 지나면 무효가 됩니다. 다만 CID가 바뀌면 SBT에 박힌 값도 갱신해야 해서 구조를 다시 설계해야 합니다.

**꼬리질문:** 그렇게 하면 블록체인의 불변성이라는 장점이 사라지지 않습니까?

#### Q015. 이 논문에서 본인 기여는 무엇입니까? 🔴

**의도:** 2저자이므로 구체적 답변이 기대된다.

**답변:** `[ 직접 작성 ]` 이 논문은 주저자가 학부생이고 제가 2저자인 대학원생이었습니다.

> **작성 안내**: 13편 중 저자 순위가 세 번째로 높은 논문이다(T01 제1저자, T02 교신저자 다음). 주저자가 학부생이므로 **대학원생으로서 지도한 형태였는지**를 확인해 채운다. 그렇다면 "학부생 연구를 지도했다"는 것 자체가 답변 소재가 된다. 문제 설정(3D 계측 데이터의 보안)을 제안했는지도 확인할 것.

**꼬리질문:** 학부생 주저자를 지도하신 겁니까?

#### Q016. 후속 연구가 있습니까? 🟢

**의도:** T13과의 연결을 아는지 본다.

**답변:** 있습니다. 이 논문의 절차 중에 잘못된 지갑 주소를 입력하면 되찾을 수 없다는 경고가 나오는데, 블록체인의 근본 성질입니다. SBT는 양도가 불가능하다는 것이 존재 이유인데, 바로 그 성질 때문에 지갑을 잃어버리면 새 지갑으로 옮길 수단이 없습니다. 이 문제를 다룬 것이 넉 달 뒤에 같은 학회지에 낸 후속 논문입니다. 기존의 가디언 개념은 공공기관을 가디언으로 세우는 방식인데 탈중앙화와 상충하고 스타트업에 부담이라, 고객들이 서로의 가디언이 되는 고객 중심 가디언 시스템을 제안했습니다. 두 논문이 저장과 복구라는 한 쌍을 이룹니다.

**꼬리질문:** 그 복구 시스템은 어떻게 동작합니까?
